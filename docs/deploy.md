# Деплой: GitHub Actions → VPS в Docker

Workflow настроен выкатывать пуши в `main` только после проверок. Ниже описано поведение конфигурации, **не подтверждение текущей выкладки**. В локальной приёмке этого обновления прошли две реальные prefixed smoke-проверки и Edge-проверки игры/админки/телефонного интерфейса; Docker daemon недоступен, `compose up`, контейнерный откат и удалённый деплой не выполнялись. Push также не выполнялся.

```
push в main
 ├─ Tests (серверы GitHub, ~2 мин)               — тот же набор проверяет каждый pull request
 │    ├─ проверка типов (сайт и сервер)
 │    ├─ юнит-тесты (физика, дорога, трафик, онлайн-сессия, модель машины)
 │    ├─ сборка сайта и сервера
 │    ├─ смоук: оба собранных мира с раздельными данными, по 3 настоящих клиента на 10 с
 │    └─ отчёт о качестве сети (npm run netcheck) — в Summary запуска
 └─ Deploy (раннер на VPS, только если Tests прошли)
      └─ deploy/deploy.sh
           ├─ сертификат для IP (один раз, на 10 лет)
           ├─ сборка образов с номером коммита (typecheck и сборка; тесты внутри — только при ручном деплое)
           ├─ docker compose up -d
           ├─ проверки снаружи, как заходит игрок:
           │    /health и /miami/health: HTTPS, правильные map и коммит
           │    обе /api/map, tuning, radio и защищённая admin API доходят до своего мира
           │    /version.json — этот коммит, страница и все её /assets/ грузятся
           │    http → https (308), сертификат выдан на этот адрес
           │    по 2 настоящих клиента через /ws и /miami/ws: вход, снимки, движение, прогноз
           └─ провал запуска/проверки → восстановление совместимых настроек и откат (:previous)
```

Тесты в сборке образа на VPS из workflow не повторяются (`SKIP_TESTS=1`): тот же набор только что прошёл в задании Tests на этом коммите. На VPS всего 2 ядра и 2 ГБ без swap, и под такой нагрузкой набор падал (коммит с Porsche: тяжёлые тесты модели и звука плюс тест на время шага физики), хотя в CI проходил. При ручном `bash deploy/deploy.sh` тесты в сборке выполняются, как раньше.

Заметка о 2 ядрах/2 ГБ и старом падении — **исторический контекст коллеги**, не новое обследование VPS. Два процесса теперь делят ресурсы машины; успешный локальный тест не доказывает запас производительности на ней.

Смоук-клиент можно запустить и руками против любого сервера:

```bash
npm run build:server
node dist-server/smoke.js --url ws://127.0.0.1:8787/ws --clients 3 --seconds 10
node dist-server/smoke.js --url ws://127.0.0.1:8788/ws --map miami --clients 3 --seconds 10
# Внешние примеры для оператора после авторизованной выкладки:
node dist-server/smoke.js --url wss://<host>/ws --map highway --origin https://<host> --insecure
node dist-server/smoke.js --url wss://<host>/miami/ws --map miami --origin https://<host> --insecure
```

## Что задаёт Compose

| контейнер | что делает | порты |
|---|---|---|
| `traffic-web-1` | Caddy: общий сайт и HTTPS; `/ws`, `/health`, `/api/*` → Highway, `/miami/ws`, `/miami/health`, `/miami/api/*` → Miami со снятием префикса | 80, 443 |
| `traffic-game-1` | Highway, `MAP_ID=highway`, Node 120 Гц | 8787, только внутри Docker |
| `traffic-game-miami-1` | Miami, `MAP_ID=miami`, тот же игровой образ, отдельный процесс | 8787, только внутри Docker |

- Контейнеры перезапускаются сами (`restart: unless-stopped`), в том числе после перезагрузки сервера.
- Логи ограничены: по 10 МБ × 3 файла на контейнер.
- Память ограничена: каждому игровому процессу 512 МБ и 1 CPU, Caddy 256 МБ и 0.5 CPU. Это верхние лимиты, не выделенные физические ядра и не измеренная нагрузка.
- Highway сохраняет SQLite и радио на `game_data`, Miami — на новом `miami_data`. Тюнинг, трафик, лидерборд, журнал и библиотека радио независимы и переживают замену образа. Сохраняйте оба тома, не используйте `down -v` при обновлении.
- БД хранит `MAP_ID`, аудиокаталог — `.map-id`. Несовпадение останавливает запуск до восстановления настроек. Заполненное старое хранилище без метки считается Highway; не копируйте его в Miami и не меняйте метку вручную.
- Общий сайт открывается как `/?map=highway` или `/?map=miami`; `/miami/` — не второй каталог статики. Healthcheck каждого игрового контейнера проверяет точные карту и версию; Caddy зависит от здоровья обоих.
- Старые образы и кэш сборки старше недели удаляются после каждого деплоя.

## HTTPS без домена

`deploy.sh` один раз делает самоподписанный сертификат на IP сервера. Сертификат лежит в `/opt/traffic/certs` и живёт 10 лет.

Браузер при первом заходе предупреждает, что сертификат недоверенный. Нажмите «Дополнительно → Перейти на сайт», дальше всё работает, включая WebSocket (`wss://` идёт на тот же адрес).

Чтобы предупреждения не было совсем, можно добавить `cert.pem` в доверенные корневые сертификаты на своих компьютерах.

Когда появится домен:
1. Задайте переменную репозитория `SITE_ADDRESS` = домен (Settings → Secrets and variables → Actions → Variables).
2. В `deploy/docker/Caddyfile` уберите строку `tls …` — Caddy сам получит сертификат Let's Encrypt.

## Первая настройка сервера

**Историческая заметка:** прежняя настройка `vps_ru` была выполнена коллегой. В этой сессии её состояние не проверялось. Для нового сервера на Ubuntu 24.04:

1. Под root запустите `bash deploy/vps-setup.sh`. Скрипт ставит:
   - swap 2 ГБ;
   - Docker с Compose;
   - пользователя `gha` в группе docker;
   - раннер в `/opt/actions-runner`.
2. Под root запустите `bash /opt/actions-runner/register.sh` (это то же, что `deploy/runner-register.sh`). Скрипт спросит токен и не покажет его на экране.
   - Токен берётся в GitHub: **Settings → Actions → Runners → New self-hosted runner**, значение после `--token` в блоке Configure. Токен действует час.
   - После регистрации раннер работает как служба systemd от пользователя `gha` с меткой `vps_ru`.
3. Сделайте пуш в `main` или запустите workflow **Deploy** вручную (Actions → Deploy → Run workflow).

## Пароль админки

Админка открывается по `https://<host>/admin.html?map=highway` или `…?map=miami`; один сайт, раздельные API и токены. `185.225.200.161` ниже — исторический адрес из настройки коллеги, не проверенный этой приёмкой. Пароль задаётся секретом репозитория:

1. GitHub → репозиторий → **Settings → Secrets and variables → Actions → Secrets → New repository secret**.
2. Name: `ADMIN_PASSWORD`, Secret: пароль (лучше 16+ символов; короче 12 сервер пишет предупреждение в журнал).
3. При разрешённом запуске **Deploy** workflow передаёт секрет в `deploy.sh`, Compose — в оба игровых контейнера. Сессии при этом всё равно независимы.

Без секрета админские API выключены. В Compose трафик по умолчанию плотный (`TRAFFIC=2`); настройки админки хранятся в БД своего мира и переживают деплой. Чтобы сменить пароль, обновите секрет и перезапустите Deploy; сессии перезапущенных процессов закончатся.

Локально: `ADMIN_PASSWORD=… npm run server`, затем `http://localhost:5173/admin.html`.

## Безопасность раннера

Репозиторий публичный. Деплой `main` и ручной Deploy используют VPS-раннер; проверка pull request (`test.yml`) идёт на серверах GitHub.

- Не добавляйте `pull_request` в `deploy.yml`.
- В Settings → Actions → General включите «Require approval for all outside collaborators».

Причина: чужой pull request иначе может запустить свой код на VPS. У пользователя `gha` есть доступ к Docker, а это фактически root.

## Ручной systemd: подготовка и перенос данных

`deploy/traffic-server.service` — одноинстансный пример Highway, не готовая пара unit-файлов для двух карт. Он явно задаёт **5 мест** (`MAX_PLAYERS=5`), хотя программный дефолт — 50. Перед запуском создайте системные **пользователя и группу `traffic`**, установите Node и файлы приложения в `/opt/traffic`, доступные этому пользователю на чтение/исполнение. Не делайте весь каталог приложения записываемым ради SQLite.

Unit задаёт `DB_PATH=/var/lib/traffic/traffic.db`, `RADIO_DIR=/var/lib/traffic/radio`; необязательный `JOURNAL_DIR=/var/log/traffic/sessions` включается отдельно. `StateDirectory=traffic` и `LogsDirectory=traffic/sessions` создают каталоги с владельцем `traffic:traffic` и правами 0700, `UMask=0077`. Они доступны для записи при сохранённых `ProtectSystem=strict`, `ProtectHome=true` и `PrivateTmp=true`.

Если данные раньше лежали в `/opt/traffic/data`, **до первого запуска обновлённого unit**:

1. Остановите старую службу и любые другие процессы, пишущие в эту БД/радиокаталог. Сделайте резервную копию и убедитесь, что ни один writer не работает.
2. Подготовьте целевые приватные каталоги с владельцем `traffic:traffic`. Перенесите **согласованный набор** конкретной базы: `traffic.db` и имеющиеся `traffic.db-wal` / `traffic.db-shm` из одного остановленного состояния, а также соответствующий каталог радио целиком (включая `.map-id`, если есть). После корректного закрытия SQLite WAL может уже отсутствовать — не создавайте его искусственно и не смешивайте с WAL от другой копии.
3. Проверьте владельца, права, содержимое и выбранную карту; старую резервную копию пока сохраните. Только затем выполняйте `daemon-reload` и запускайте unit, проверяя журнал, health и доступность библиотеки.

Не копируйте широко `/opt/traffic` поверх `/var/lib/traffic`, не копируйте только основной файл **работающей** SQLite и не запускайте новый процесс между переносом БД и радио. Для Miami нужен отдельный unit с собственными портом, `MAP_ID`, каталогами state/log/radio и прокси-маршрутами; два unit не должны делить SQLite или радио.

После успешной сборки `deploy/deploy.sh` останавливает web и оба игровых процесса. До запуска новой версии `deploy/rollback-settings.mjs` читает настройки каждой БД через SQLite-транзакцию, включая WAL, и сохраняет приватный snapshot в соответствующем `/data`. При неудачном запуске/проверке сначала восстанавливается только несовместимо мигрированная запись `tuning`, затем запускаются предыдущие образы. Заезды, таблицы рекордов, загрузки радио и изменения прочих настроек не откатываются. Изменения тюнинга той же ревизии сохраняются. Неизвестная миграция или ошибка восстановления оставляет серверы остановленными и snapshots на месте; сырые настройки и ошибки с их содержимым не печатаются. При первой выкатке Miami без подтверждённого предыдущего Miami-образа восстанавливается только Highway, Miami-volume сохраняется. После успешной проверки snapshots удаляются. Этот механизм проверен SQLite/WAL и mocked-Docker тестами, **не реальным контейнерным откатом**. Старые прокси-примеры не следует считать готовой production-конфигурацией доверия к заголовкам.

## Доверие к прокси и адрес клиента

Точное имя переменной — **`TRUSTED_PROXIES`**: список IP/CIDR через запятую. Пустое значение не доверяет никому, неверная запись останавливает запуск. Для прямого standalone-сервера оставьте её пустой. Не доверяйте всей сети ради удобства.

HTTP API и WebSocket используют один настроенный resolver (`server/clientAddress.ts`, в API передаётся как `ApiOptions.clientAddress`). `X-Forwarded-For` принимается только от проверенного socket-peer из allowlist; цепочка разбирается справа налево до первого недоверенного узла. Прокси обязан перезаписывать XFF либо добавлять реальный адрес своего клиента. Цепочка ограничена 32 hops и 4096 символами; неверная цепочка целиком отбрасывается в пользу адреса сокета. IPv4-mapped IPv6 нормализуется к IPv4, чтобы не создавать разные ключи лимитера/бана для одного адреса.

Compose доверяет **только фиксированному адресу Caddy** `PROXY_IP` (по умолчанию `172.30.114.2`) в отдельной сети `client_proxy`. По умолчанию `PROXY_NETWORK_SUBNET=172.30.114.0/24`, динамический `PROXY_NETWORK_IP_RANGE=172.30.114.128/25`: адрес Caddy находится внутри subnet, но вне динамического пула. При переопределении меняйте все связанные значения согласованно; не допускайте пересечения статического IP с пулом и конфликтов с сетью хоста.

Админские rate limits и аудит намеренно сохраняют защищённый **socket-only** resolver: за Caddy в аудите будет адрес Caddy, а не переданный XFF. Это не ошибка маршрутизации и не обещание реального IP администратора. Локальная проверка прежнего address-spoof сценария: из 45 solo-запросов 20 приняты, 25 ограничены; это результат конкретной проверки, не общий лимит БД или подтверждение production-деплоя.

## Полезные команды на сервере

```bash
cd /opt/actions-runner/_work/traffic_cutting_up/traffic_cutting_up   # последняя выкатка
docker compose ps                        # состояние, здоровье
docker compose logs -f --tail 100 game   # логи игрового сервера
docker compose logs -f --tail 100 game-miami  # отдельный мир Miami
curl -sk https://localhost/health        # метрики сервера (через Caddy)
curl -sk https://localhost/miami/health  # карта должна быть miami, версия — ожидаемый коммит
docker compose exec game node dist-server/logs.js 100     # журнал проблем (сервер и страницы игроков)
docker compose exec game node dist-server/logs.js top solo  # лидерборд (solo | online)
docker compose exec game-miami node dist-server/logs.js top online  # отдельная таблица Miami
systemctl status 'actions.runner.*'      # раннер
journalctl -u 'actions.runner.*' -f      # логи раннера
```

Проверка оператором после выкладки: `/version.json` для сайта, поля `version` и `map` в `/health` и `/miami/health`; `/api/map` и `/miami/api/map` также должны назвать свои карты. Один HTTP 200 недостаточен: Highway не может считаться успешным Miami. Требуются две внешние smoke-проверки с правильным `--map`.

Откат:
- если новая версия не прошла запуск/проверки, `deploy.sh` пытается вернуть прошлые образы. При первом Miami-rollout без подтверждённого прошлого Miami он останавливает новый процесс, сохраняет `miami_data` и восстанавливает только Highway/web; старый Highway-бинарник не запускается под видом Miami. Если прошлых образов нет или восстановление не удалось, нужен оператор. Этот путь ещё не проверен на Docker daemon в текущей среде;
- откатиться вручную: Actions → Deploy → прошлый успешный запуск → **Re-run all jobs**, он соберёт и выкатит тот коммит.
