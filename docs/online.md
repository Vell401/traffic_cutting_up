# Онлайн-режим

Два независимых сервера: Highway и Miami, каждый со своим кольцом 12 км, трафиком и хранилищем. По умолчанию 50 водителей на мир, настраивается 1–64. Кузова/физика: Porsche 1/4, R34 2/2, A45 3/3, C63 W204 4/5; выбор кузова в игре включает соответствующую физику. Совместимый Grip (PhysicsId 1) остаётся в протоколе и админке, но не отдельным пунктом игрового меню. Трафик задаёт выбранный сервер. Полная инструкция: [mobile-miami-upgrade.md](mobile-miami-upgrade.md).

## Как запустить локально

```bash
npm install
npm run server        # Highway на :8787 (перезапускается при правке кода)
npm run dev           # сайт на :5173, /ws, /health, /api проксируются на :8787
```

Откройте http://localhost:5173 (онлайн открывается по умолчанию; одиночный режим — `?solo`), введите имя и нажмите «Подключиться». Вторая вкладка или другой компьютер в сети (`http://<ip>:5173`) — второй водитель.

Для Miami запустите отдельный процесс с `MAP_ID=miami PORT=8788` и отдельными `DB_PATH` / `RADIO_DIR` (синтаксис Bash; в PowerShell используйте `$env:…`). Vite снимает `/miami` с backend-маршрутов и направляет их на 8788 (`GAME_MIAMI_SERVER` меняет адрес); Highway использует `GAME_SERVER`. В игре откройте `/?map=miami`, в админке — `/admin.html?map=miami`. Выбор карты запоминается, явный URL имеет приоритет. Два процесса нельзя направлять на одну БД или аудиокаталог.

Если хотите проверить одни, запустите ботов (полноценные клиенты с прогнозом и автопилотом):

```bash
npm run bot           # 2 бота на ws://localhost:8787/ws
npm run bot -- 4      # 4 бота
```

Плохая связь имитируется в адресе страницы: `?online&lag=150&jitter=50&stall=0.01` (добавочный RTT в мс, джиттер в мс, вероятность паузы на 250 мс на сообщение). `F1` показывает строку `net`: пинг, на сколько шагов клиент впереди сервера, глубину очереди ввода на сервере, число и размер исправлений.

## Устройство

```
src/sim/maps.ts          реестр карт, ревизии, темы и защита спавна
src/sim/ring.ts          Highway: 3 одинаковые трети по 4 км, каждая поворачивает ровно на 120°
src/sim/miami.ts         Miami: 4 четверти по 3 км, каждая поворачивает ровно на 90°
src/sim/traffic.ts       трафик вокруг нескольких водителей, расстояния по кольцу, поиск соседей по отсортированному списку
src/sim/contact.ts       столкновения машины с трафиком (общие для одиночки, сервера и прогноза)
src/online/rules.ts      правила сессии, которые задаёт сервер, и хеш версии правил
src/online/protocol.ts   формат сообщений (JSON для редких, бинарные INPUT и SNAPSHOT)
src/online/world.ts      авторитетный мир сервера: водители, очереди ввода, трафик, очки, журнал
src/online/gameServer.ts сессии, переподключение, проверка ввода, рассылка снимков, метрики (без сокетов)
src/online/clientCore.ts прогноз и сверка на клиенте (без DOM, работает и в тестах)
src/online/session.ts    браузер: WebSocket, переподключение, токен
server/main.ts           Node: HTTP /health, WebSocket /ws, цикл 120 Гц, журнал, логи
tests/netsim.ts          сервер и клиенты в одном процессе через имитацию сети
scripts/netcheck.ts      отчёт о качестве езды при разных задержках
```

### Время и ввод

- Сервер считает мир шагами по 120 Гц. Клиент нумерует свой ввод (`seq`) по одному на шаг и шлёт пачкой раз в кадр.
- Сервер применяет ввод каждого водителя строго по порядку, по одному на шаг:
  - если ввода нет, машина ждёт;
  - если в очереди больше 6 вводов, сервер применяет два за шаг и догоняет.

  Каждый ввод применяется ровно один раз, поэтому клиент может предсказать свою машину точно.
- Ввод квантуется **до** того, как клиент его применит: руль — 16 бит, педали — 8 бит. Обе стороны считают на одних и тех же числах.
- **Флаги ввода:**
  - аналоговый руль;
  - ручная коробка;
  - переключение вверх или вниз — оно лежит ровно в одном вводе, поэтому сервер и прогноз переключают передачу на одном и том же шаге;
  - поворотник — сервер передаёт его остальным в снимке.
- Снимок (30 в секунду) содержит:
  - номер шага сервера;
  - номер последнего применённого ввода (`ack`) и полное состояние машины после него — 28 float64 для Grip, 58 для R34, 47 для осевых моделей A45/Porsche/C63 (буфер до 64);
  - очки;
  - других водителей: 36 байт на каждого, включая 8 байт четырёх signed int16 omega (масштаб 16, шаг 1/16 рад/с); фактический угол колёс передаётся для всех кузовов;
  - трафик в окне −260…+1000 м.

Телеметрия колёс — только для наблюдателя/эффектов; она не заменяет полный state владельца и не меняет физику. Машина трафика занимает 26 байт. Формула размера snapshot без транспортных заголовков: `54 + 8 × stateLen + 36 × remoteDrivers + 26 × trafficCars` байт; единого постоянного размера снимка нет.

### Прогноз на клиенте

- **Своя машина.** Едет сразу по своему вводу, ввод хранится. На каждом снимке машина откатывается к состоянию сервера на `ack`, неподтверждённые вводы проигрываются заново. Без контактов результат совпадает с сервером до бита: координата `s` у машины одна и та же число в число (круги не сворачиваются), а кривизна кольца берётся из шаблона круга.
- **Трафик.** Приходит в состоянии на момент `ack` и проматывается вперёд до текущего шага клиента: постоянное ускорение, перестроения по их кривой, разбитые машины скользят. Поэтому машина встречает трафик там, где его встретит сервер. При каждой сверке контакты пересчитываются; задетая машина ведёт себя как разбитая, пока сервер её не догонит.
- **Другие водители.** Их последнее состояние проматывается вдоль скорости до того же шага.
- **Расхождения.** То, что всё же прыгнуло (чужие решения, которых клиент не мог знать), рисуется со смещением, затухающим примерно за 0.1 с.
- **Горизонт прогноза** около RTT плюс буфер очереди: 1–2 шага в LAN, около 17 при 80 мс, около 28 при 150 мс.

### Трафик на кольце

- У каждого водителя своё окно −220…+850 м, общая плотность в нём держится на уровне, который задаёт директор.
- Машина пропадает, только когда не попадает ни в одно окно.
- Новые машины появляются только там, где их не видит ни один другой водитель: не ближе 680 м впереди и не ближе 200 м позади любого из них.
- Обломки остаются общими препятствиями: машину убирают через 15 с, если рядом никого нет, и в любом случае через 60 с.
- Режимы трафика меняются примерно раз в 40 с, все видят одну и ту же смену.

### Контакты

- **Водители сталкиваются друг с другом.** Сервер проверяет каждую пару активных машин: они расталкиваются по массе и обмениваются импульсом. Отскок и закрутка слабые: машину толкает, но не крутит волчком. Клиент в своём прогнозе сталкивается с предсказанными чужими машинами так же, как с трафиком, поэтому толчок чувствуется сразу, без ожидания сервера.
- **Жёсткий удар — авария.** Если скорость сближения 8 м/с (около 29 км/ч) и больше, заезд заканчивается у обоих.
- **Мягкое касание — толчок.** Обрывает комбо обоим, заезд идёт дальше.
- **Долгое трение — одно событие.** Пока машины не разошлись на полсекунды, повторного события нет.
- **Кто не сталкивается.** Призраки после спавна и машины «в боксах» проходят сквозь всех.
- **Трафик.** Удар о машину трафика заканчивает заезд, даже если это чужой обломок. Цепных аварий NPC пока нет.

### Спавн и респаун

- **Все появляются в одной точке выбранного мира** — на правой обочине: Highway 7.8 км, Miami 300 м (`src/sim/maps.ts`). Это один общий защищённый pad, не пять персональных парковочных мест.
- **Пока машина на площадке, она призрак.** Другие её не видят вовсе, трафик и игроки проходят насквозь. Свою машину вы видите полупрозрачной. Защита держится не меньше 3 с, а дальше, пока машина стоит на обочине у площадки, касается трафика или другого игрока. Поэтому даже 50 человек, стартующих из одной точки, не сталкиваются.
- **При входе и по R** машина стоит в этой точке с нуля, R заканчивает заезд. Если вы уже на другом круге, телепортирует на ближайший по кругу экземпляр точки.
- **Справа сверху в таблице** у каждого водителя показано расстояние по кольцу кратчайшим путём: ▲ — впереди, ▼ — позади.

### Лидерборд

Лучший заезд каждого игрока хранится на выбранном сервере в SQLite (`server/store.ts`, файл `DB_PATH`). У карт разные БД; одиночный режим и онлайн внутри каждой ведутся отдельно:
- **онлайн** — заезды засчитывает сам сервер по своему подсчёту очков;
- **одиночный** — заезд присылает страница, когда он заканчивается: `POST /api/runs`, имя берётся из поля «Имя». Сервер проверяет границы значений и ограничивает частоту, но в целом верит странице.

В таблицу попадают заезды от 1 000 очков. В меню она справа, с вкладками «Одиночный / Онлайн» (`GET /api/leaderboard?mode=solo|online`).

Для Miami внешний путь — `/miami/api/leaderboard`; solo-запрос содержит `map: 'miami'`. API возвращает карту и `soloPolicy: 'selected-instance'`. Старые solo-запросы без карты принимаются только Highway. Локальные best/sky и reconnect-токены также разделены по карте/endpoint.

Solo-записи ограничены суммарно **120 допусками к записи за скользящую минуту на API-instance** (в памяти не более 120 timestamps), независимо от числа адресов. Этот бюджет расходуют только валидные запросы с правильной картой и счётом от 1000; неверные и результаты ниже порога его не расходуют. Отдельный per-address limiter остаётся на 20 запросов в своём окне (`Limiter` в `server/api.ts`). Это ограничение **скорости записи**, не пожизненный лимит количества строк SQLite и не новая проверка честности solo-результата.

### Диагностика

В ту же базу пишется журнал проблем, примерно 20 000 последних строк.

**Сервер записывает:**
- запуск (версия, правила, зерно);
- необработанные исключения со стеком;
- такт дольше 8 мс;
- отставание с потерей шагов;
- память больше 400 МБ;
- свои предупреждения и ошибки (нарушения протокола, отключения).

Одинаковые строки за минуту схлопываются в одну.

**Страница игрока присылает** (`POST /api/log`) ошибки скриптов, потерю контекста WebGL, сбой загрузки модели, отказ сервера и долгие переподключения, поправку прогноза больше 3 м и FPS ниже 24 в течение 10 с. К записи добавляются браузер и видеокарта.

**Ограничения:** не больше 30 сообщений за загрузку страницы и 10 запросов с адреса за 10 минут, всего 300 строк от страниц и 150 от сервера за 10 минут.

**Прочитать:** в админке (ниже) или `docker compose exec game node dist-server/logs.js 100` (или `… logs.js 200 client`, `… logs.js top online`).

### Админка

Страница `/admin.html?map=highway|miami` (`src/admin/`, API — `server/admin.ts`). Работает, только если на выбранном сервере задан `ADMIN_PASSWORD`; иначе его `/api/admin/*` отвечает 404. Внешний Miami-префикс — `/miami`. Пароль в настроенном workflow попадает из секрета репозитория (см. [deploy.md](deploy.md)). Шесть вкладок и сохранение форм описаны в [admin-settings-radio.md](admin-settings-radio.md).

Что можно:
- **состояние**: игроки и места, соединения, машин трафика, время такта, память, аптайм, версия;
- **трафик на ходу**: включить или выключить (выключение сразу убирает все машины), режим (авто или закрепить: обычный, свободный, плотный, грузовики, стенки, колонны). Старые переключатели общей плотности и сложности удалены; `TRAFFIC=2` задаёт исходный пресет Compose, если нет сохранённых настроек;
- **спавн по режимам**: прямые цели 0–80 машин на 1 км полосы и оценка числа вокруг одного игрока, без скрытых множителей. Настройки трафика сохраняются в БД выбранного мира и применяются при старте;
- **тюнинг и радио**: формы всех профилей, отдельный сброс машины/скоростей, библиотека с загрузкой треков; изменения относятся только к этому серверу;
- **игроки**: список со скоростью, очками, адресом, нарушениями; отключить, отключить с баном адреса на 30 мин или сутки; снять бан;
- **места на сервере** (1–64) и **объявление**: крупная плашка «Сообщение сервера» на 9 с у всех подключённых (поверх меню тоже), со звуком, и строка в ленте событий;
- **лидерборд**: удалить все заезды игрока из одиночной или онлайн-таблицы (против подделанных одиночных результатов);
- **журнал**: последние 300 строк, отдельно сервер и страницы игроков.

Защита: вход по паролю (сравнение за постоянное время), сессия на 12 ч в памяти сервера, токен живёт только во вкладке. Неверный пароль — не больше 8 попыток с адреса и 40 всего за 10 минут. Изменения только JSON-запросами со своих страниц. Каждое действие и каждый вход пишутся в журнал с адресом.

Изменения трафика и мест пишутся в журнал сессии как стимул `config`, поэтому повтор сессии по журналу остаётся точным.

### Сворачивание вкладки и обрывы

- **Нет ввода 0.75 с** (вкладка свёрнута, связь встала): машина уходит с дороги («в боксах»). Когда ввод возобновится, она вернётся туда, где была (не на площадку), на 90 км/ч и призраком.
- **Оборванное соединение.** Клиент переподключается сам с паузами от 0.5 до 10 с. Слот, очки и рекорд держатся 60 с. Токен лежит в `sessionStorage`, поэтому даже перезагрузка вкладки возвращает в тот же слот.

### Защита сервера

- WebSocket пропускает сообщения до 16 КБ, не больше 400 в секунду с одного соединения.
- Respawn принимается не чаще одного раза на водителя за секунду симуляции; повторное подключение не обходит этот водительский cooldown. При backpressure запрос также пропускается. Это не пауза мира и не новый физический таймер.
- Ввод допускается по водительскому временному бюджету 120 шагов/секунду с начальным опережением до 8 вводов и накоплением не более `inputMax`. Время процесса и тики сервера — альтернативные часы, не складываемые кредиты; переподключение не пополняет бюджет. После более 50 нарушений соединение закрывается. Формулы автомобиля при этом не меняются.
- Число соединений ограничено независимо от занятых слотов: `16 + 2 × clamp(maxPlayers, 0, 64)` (18 при одном месте, максимум 144). Без успешного hello соединение истекает через 5 секунд серверных тиков, даже если отвечает на ping. Лишний upgrade получает HTTP 503; нормальные reconnect проходят отдельную проверку токена.
- При окончательном удалении водителя (истечение reconnect grace, kick/ban, смена физической модели) текущий непустой заезд завершается и передаётся в хранилище один раз. Во время самого grace и косметического reconnect заезд сохраняется без преждевременной записи.
- Если клиент забегает дальше очереди в 240 вводов, старые вводы отбрасываются и засчитываются как нарушение.
- Имена очищаются, поддерживаются PhysicsId 1–5 и CarId 1–4.
- Клиент с другой версией протокола/правил получает отказ «обновите страницу», с другой картой — отказ карты. **Протокол 12**: флаги ввода 16-битные (включая отдельные boost/clutch и состояние ассистов); сигнал виден как `REMOTE_HORN`, у трафика есть смещение в полосе. `hello`/`welcome` проверяют карту, а клиент дополнительно проверяет её ревизию, длину кольца и rules hash до применения state/tuning.
- Медленному клиенту снимки не копятся: при очереди отправки больше 256 КБ они пропускаются, при 4 МБ клиент отключается.

### Воспроизводимость

- Мир детерминирован: зерно и все внешние события (вход, выход, ввод, респаун, пересинхронизация), помеченные номером шага, однозначно задают сессию.
- С `JOURNAL_DIR` сервер пишет журнал в NDJSON, размер ограничен `JOURNAL_MAX_MB`.
- `replay()` из `src/online/world.ts` восстанавливает мир по журналу. Тест проверяет, что хеш состояния совпадает с живой сессией.

## Исторические измерения качества езды (этап 3)

Ниже сохранён результат прежнего `npm run netcheck`, **до текущих R34/карт/протокола**: сервер и два бота, 60 с на случай. Он не описывает текущую сборку. Столбец «исправления» — сколько раз сервер поправил прогноз и на сколько сантиметров (p50 / p95 / max):

| случай | впереди, шагов | исправлений | p50 | p95 | max |
|---|---|---|---|---|---|
| LAN | 1 | 2 | 0 | 0 | 0 |
| 30 мс | 7 | 72 | 0 | 0.4 | 1.4 |
| 80 мс ±30 | 17 | 40 | 0 | 2.8 | 3.0 |
| 150 мс ±50 | 28 | 72 | 1.6 | 10 | 15 |
| 150 мс, паузы 250 мс | 31 | 36 | 2.0 | 28 | 40 |
| 80 мс, 30 FPS | 16 | 77 | 0.2 | 3.7 | 7.3 |
| 80 мс, 20 FPS | 15 | 80 | 4.1 | 27 | 88 |
| 80 мс, аварии | 16 | 501 | 0.4 | 3.2 | 77 |
| 150 мс, аварии, 30 FPS | 26 | 583 | 1.2 | 18 | 444 |

В тестах без контактов прогноз может совпадать точно; это не гарантия отсутствия коррекций при любой сети. Цифры таблицы получены на синтетических ботах. Их нужно перепроверять на настоящих проездах людей, а не судить только по плавности картинки.

**Отдельный измеренный предел R34:** стресс при 150 мс со stalled contacts дал **2.639 м max** (около **35 см p95**; прежнее округление 2.64 м). Корректный rewind не устраняет несовпадение предсказанного контакта и серверного или паузы доставки; это известное ограничение, а не скрытый успешными тестами результат. Для повторного отчёта: `npm run netcheck -- 60 --map highway` и `npm run netcheck -- 60 --map miami`; новая выборка может отличаться.

## Развёртывание (этап 6)

Настроенный путь — Docker и автодеплой после CI: два игровых процесса с независимыми томами, общий Caddy, проверка обеих карт. Всё описано в [deploy.md](deploy.md). Для этого обновления локально прошли оба prefixed smoke и интегрированный Edge, но Docker daemon недоступен, контейнерный/удалённый деплой не выполнялся. Ниже — ручной вариант без Docker; для двух карт нужны два процесса и маршрутизация префикса.

Сайт — статика (`npm run build` → `dist/`) на любом облачном хостинге. Игровой сервер — Node 22+ на VPS за HTTPS/WSS-прокси.

1. Сборка сайта с адресом сервера:
   ```bash
    VITE_ONLINE_URL=wss://game.example.com/ws VITE_MIAMI_ONLINE_URL=wss://game.example.com/miami/ws npm run build
   ```
    Без переменных клиент идёт на `/ws` для Highway и `/miami/ws` для Miami того же хоста (wss на HTTPS, ws на HTTP). Произвольный `?server=` имеет приоритет; HTTP API/health вычисляются рядом с WebSocket с сохранением префикса.
2. Сборка сервера и копирование на VPS:
   ```bash
   npm run build:server          # dist-server/main.js (+ ws из node_modules)
   rsync -a dist-server package.json package-lock.json user@vps:/opt/traffic/
   ssh user@vps 'cd /opt/traffic && npm ci --omit=dev'
   ```
3. Автоперезапуск: [deploy/traffic-server.service](../deploy/traffic-server.service) (systemd: `Restart=always`, лимит памяти, журнал через journald с ограничением размера).
   До запуска создайте пользователя/группу `traffic`; БД/радио теперь находятся под `/var/lib/traffic`, необязательный журнал — `/var/log/traffic/sessions`. При переносе сначала остановите writers и перенесите согласованные SQLite/WAL/радио, не копируйте работающую БД. Пошаговые требования и сохранённый strict sandbox — в [deploy.md](deploy.md#ручной-systemd-подготовка-и-перенос-данных).
4. TLS и WebSocket-прокси: [deploy/Caddyfile](../deploy/Caddyfile) или [deploy/nginx.conf](../deploy/nginx.conf) — **старые одноинстансные примеры**. Для Miami добавьте отдельный upstream и снятие `/miami` для ws/health/api, как в [deploy/docker/Caddyfile](../deploy/docker/Caddyfile); не направляйте обе карты на Highway.
5. Переменные окружения сервера:

   | переменная | значение |
   |---|---|
    | `PORT` | порт, по умолчанию 8787 |
    | `MAP_ID` | `highway` (по умолчанию) или `miami`; неизвестное значение останавливает запуск |
   | `ORIGINS` | список разрешённых адресов сайта через запятую; в продакшене обязательно |
    | `MAX_PLAYERS` | 1–64, по умолчанию 50 |
   | `TRAFFIC` | 1 обычный, 2 плотный |
   | `INTENSITY` | сложность 0…1 |
   | `SEED` | зерно мира |
   | `JOURNAL_DIR`, `JOURNAL_MAX_MB` | журнал сессии |
    | `LOG_EVERY` | период строки статуса в логе, с |
    | `DB_PATH` | отдельный файл SQLite; по умолчанию `data/traffic.db` или `data/miami/traffic.db` |
    | `RADIO_DIR` | отдельный аудиокаталог, по умолчанию `radio/` рядом с БД |
    | `TRUSTED_PROXIES` | IP/CIDR через запятую для доверенных socket-peer; пусто = не доверять XFF, неверно = отказ запуска |
6. Контроль:
   - `GET /health` отдаёт шаг, игроков и соединения, среднее и максимальное время шага, трафик, память (RSS, heap), отправленные и пропущенные снимки, очередь и нарушения каждого водителя.
   - Раз в `LOG_EVERY` секунд в лог пишется строка статуса.
    - Логи ограничены: не больше 50 строк за 10 с.

HTTP API и WS используют общий resolver адреса: XFF только от разрешённого peer, разбор справа налево, до 32 hops/4096 символов, при ошибке — socket-address; IPv4-mapped IPv6 нормализуется. Админка сохраняет socket-only аудит. Точная настройка Caddy и выделенной сети — в [deploy.md](deploy.md#доверие-к-прокси-и-адрес-клиента).

Исторический одноинстансный замер: шаг с двумя водителями и ~60 машинами занимал около 0.05 мс из 8.3 мс, снимок около 1.1 КБ (~35 КБ/с). Это не текущий бюджет протокола 12; используйте формулу выше и локальные [измерения нагрузки](performance.md), не переносите их автоматически на VPS.
